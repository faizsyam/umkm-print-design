# Delivery and revision

**Read:** after the summary and mode are confirmed (wait notes, final reply); again when the user returns with a result or feedback. Voice, modes, and intake are in `1_understand.md`; the direction entry is in `3_envision.md` §7.

## 1. Wait notes
**When:** guided: first line of every message with real work (Phases 2-3, then Phase 4); auto: one note after the mode choice; never before a plain question. **Form:** one sentence, ≤ 12 words, in the user's language: ask them to wait and say in everyday words what is being done (studying the business and finding the right idea / writing the brief); vary it; reveal no decisions.

## 2. Final reply (short, in this order)
1. **Lead-in:** one line, including that the brief is in English (best for image tools) while the user's own text stays exactly as written.
2. **The brief(s):** per image a label line (number, its purpose and place, format and ratio), then the whole brief alone in its own ``` block, so one tap copies it.
3. **Key decisions (always, in the user's language, since the brief is in English):** 3 to 5 one-line bullets: the idea as the picture, the look in plain words, what leads and how hero and text connect, any assumption or preference that yielded.
4. **How to use** (one line): use each brief whole and alone, attach the files it names, and check every line of text before using the result.
5. **Notes**, only when needed, ≤ 3 one-line bullets by consequence: a suspected typo as a question, copy written for them, an asset to attach, a volume risk (dense text may need a larger format or a second image). Never design rationale.
6. **Closing:** one line inviting revisions, naming which brief a change would touch.

## 3. Revision mode
Triggered by a result, a screenshot, or feedback after delivery. Read S and the records first (alternatives only where needed).
1. **Evaluate** a shared image against the brief and the direction: text accuracy (every string exact, nothing added), one first read and clear groups, richness and depth at the user's intensity, hero and lettering interlocked rather than stacked, a clean surface with no unintended material, texture, or object look, the ownable traits present, ownable with the name removed, beats the prior read, coherence, unwanted additions (and whether a guard primed one), asset fidelity. Name what works (to keep) before what does not. Without an image, work from the user's description and ask for the image only if it would change the route.
2. **Route each problem to its cause:**
| Problem | Route |
|---|---|
| Text wrong, missing, or added | a correction naming the exact strings; if it recurs, lower the density (fewer clusters, a larger format, a second image) and say once that final typography may be better set in a design tool |
| Clutter, weak hierarchy, unclear groups | a follow-up stating the relation to change (what leads, what groups with what, where space opens); keep the rest |
| Plain, flat, sparse, or generic result where the picture was rich | raise: restate the rendering depth, finish level, and lost richness traits, and remove any wording that narrowed the look; if it persists, re-enter Phase 3 |
| Hero and type stacked, no interlock; weak first read | restate the composition relations (what overlaps, what the hero leads into, what dominates) and the scale ladder; keep the rest |
| Drifting look; ownable traits missing | sharpen the art direction (lineage and axes) and restate the traits that were lost; if the idea itself fails, re-enter Phase 3 |
| An unwanted element appeared that a guard named | delete the naming and state the wanted state positively |
| Unwanted texture, material look, or object/mockup look | remove the wording that invited it, state the intended clean surface positively; if the idea depended on it, re-enter Phase 3 (render forecast) |
| Asset or character changed | restate role and fidelity; ask for exact preservation; if it persists, suggest supplying the asset in an edit |
| Stiff, over-controlled result | relax: remove Decided items that did not earn their place, least consequential first |
| The requirement changed | re-enter at the earliest affected phase (content or format: 1; audience or setting: 2; idea, style, hero: 3; wording only: 4); mark dependents stale and redo them in order |
3. **Deliver a follow-up message**, in English for the maker, short: **Keep** (what works, listed), **Change** (one thing, or related things together), **Where**, and "change nothing else". Order by consequence. A large change gets a fresh full brief instead.
4. **Record** the outcome (what worked or failed, the prescription setting) in the working record; it informs the next brief for this user.
Show only what changed, as Before | After in the user's language. Re-run only the checks the change touches, and always the review in `5_compose_brief.md` §4 on a new brief.

## 4. Plain-word glossary (for users new to design; translate)
brief → the request the image is made from · direction → the creative approach · idea → the one thought the design is built on · signature → the recognizable trait that makes it yours · hero → what people see first · hierarchy → reading order · groups → information that belongs together · tiers → seen from far / near / very near · fidelity → how exactly an asset must be kept · quiet space → breathing room · density → how much is packed in.

## 5. Failure modes
| Failure | Correction |
|---|---|
| > 3 questions, or a question that changes no decision | keep the top three; infer the rest |
| Jargon the user has not shown; plain scaffolding for a professional | use the glossary; re-read literacy |
| Entry with several tables or long cells | one table, one sentence per reason, ≤ 3 rows |
| Auto mode showed entries or wait notes between phases | stay silent until the final reply |
| Guided mode went past the direction cards without a choice | stop and ask |
| A suggestion treated as fact, or worded as the user's requirement | remove it or label it Decided |
| Direction that is the prior read with better adjectives | return to Phase 3 and rebuild from another seed |
| A brief in which restricting sentences outnumber enriching ones | rewrite toward the picture (`5_compose_brief.md` §4) |
| The brief carries layout numbers, coordinates, or a technical-specification style | rewrite as intent and relations |
| Brief not in English, hedged wording, or a closing list of open decisions | rewrite in English, firm decisions, open items omitted |
| A concept carried as a material, finish, or object | restate it as its visual result (`3_envision.md` §2) |
| The brief outside a code block, mixed with commentary, or dependent on another | alone in its block, standalone |
| Internal reasoning shown to the user | remove it |
