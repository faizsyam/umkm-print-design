# Delivery, revision, and calibration

**Read:** after the summary and mode are confirmed (wait notes, final reply); again when the user returns with a result or feedback. Voice, modes, and intake are in `1_intake.md`; the direction entry is in `3_direction.md` §5.

## 1. Wait notes
**When:** guided: first line of every message with real work (Phases 2-3, then Phase 4); auto: one note after the mode choice; never before a plain question. **Form:** one sentence, ≤ 12 words, in the user's language: ask them to wait and say in everyday words what is being done (studying the context and finding the right idea / writing the brief); vary it; reveal no decisions.

## 2. Final reply (short, in this order)
1. **Lead-in:** one line.
2. **The brief(s):** per image a label line (number, its purpose and place, format and ratio), then the whole brief alone in its own ``` block, so one tap copies it.
3. **Key decisions (auto only):** 3 to 5 one-line bullets: the idea, the look, what leads, what was left to ChatGPT, any assumption or preference that yielded.
4. **How to use** (≤ 4 steps, user's language): (1) open a new ChatGPT chat with image generation and paste the whole brief as one message; attach any supplied file the brief names, in the same message; (2) let ChatGPT decide the layout, then check every line of text (names, numbers, addresses); (3) change one thing at a time, using the follow-up lines offered on request, or send me the result for help; (4) ChatGPT returns a fixed-size image: for print, enlarge it with an upscaler afterwards and check small text first (A3 at 300 dpi is about 3,500 × 4,950 px). Optional, once: to see whether this brief helps, also try the original brief in a second chat and compare.
5. **Notes**, only when needed, ≤ 3 one-line bullets by consequence: a suspected typo as a question, copy written for them, an asset to attach, a volume risk (dense text may need a larger format or a second image). Never design rationale.
6. **Closing:** one line inviting revisions, naming which brief a change would touch.

## 3. Revision mode
Triggered by a result, a screenshot, or feedback after delivery. Read S and the record first (Basis and rejected options only where needed).
1. **Evaluate** a shared image against the ledger: intent, text accuracy (every string exact, nothing added), hierarchy (one first read, groups clear), coherence, unwanted additions, asset fidelity. Name what works (to preserve) before what does not. Without an image, work from the user's description and ask for the image only if it would change the route.
2. **Route each problem to its cause:**
| Problem | Route |
|---|---|
| Text wrong, missing, or added | a correction naming the exact strings; if it recurs, lower the density (fewer clusters, a larger format, a second image) and say once that final typography may be better set in a design tool |
| Clutter, weak hierarchy, grouping | a follow-up stating the relation to change (what leads, what groups with what, where space opens); preserve the rest |
| Generic or drifting look | strengthen the defining traits of the failing item (dial Firm); if the idea itself fails, re-enter Phase 3 |
| Asset or character changed | restate role and fidelity; ask for exact preservation; if it persists, suggest supplying the asset in an edit |
| Stiff, over-controlled result | dial Lean: remove Directed or Recommended items that did not earn their place |
| The requirement changed | re-enter at the earliest affected phase (content or format: 1; audience or setting: 2; idea, style, hero: 3; wording only: 4); set dependents stale and redo them in order |
3. **Deliver a follow-up message for the same ChatGPT conversation**, short: **Keep** (what works, listed), **Change** (one thing, or related things together), **Where**, and "change nothing else". Order by consequence. A large change gets a fresh full brief instead.
4. **Record** the outcome (what worked or failed, the dial setting) in the working record; it informs the next brief for this user.
Show only what changed, as Before | After in the user's language. Re-run only the checks the change touches, and always the self-check (`4_brief_composition.md` §4) on a new brief.

## 4. Calibration (the skill proves itself)
The architecture rests on tagged assumptions (`0_foundation.md`). On a user's first deliveries, invite the one comparison that tests them: the original brief against the skill's brief, same settings, same chat type. Record the verdict. If the skill's brief does not win, reduce prescription (dial Lean) before adding anything; if ChatGPT ignores a Directed trait, make that one trait more explicit (dial Firm). Never infer a rule from a single result.

## 5. Plain-word glossary (for users new to design; translate)
brief → the request ChatGPT will read · direction → the creative approach · hero → what people see first · hierarchy → reading order · groups → information that belongs together · tiers → seen from far / near / very near · fidelity → how exactly an asset must be kept · open decision → something ChatGPT chooses · quiet space → breathing room · density → how much is packed in.

## 6. Failure modes
| Failure | Correction |
|---|---|
| > 3 questions, or a question that changes no decision | keep the top three; infer the rest |
| Jargon the user has not shown; plain scaffolding for a professional | use the glossary; re-read literacy |
| Entry with several tables or long cells | one table, one sentence per reason, ≤ 3 rows |
| Auto mode showed entries or wait notes between phases | stay silent until the final reply |
| Guided mode went past the direction cards without a choice | stop and ask |
| A suggestion treated as fact, or worded as the user's requirement | remove it or label it Directed |
| The brief arrives with layout numbers, coordinates, or an image-prompt style | rewrite as intent and relations |
| The brief outside a code block, mixed with commentary, or dependent on another | alone in its block, standalone |
| Internal reasoning shown to the user | remove it |
